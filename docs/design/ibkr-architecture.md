# IBKR 实盘量化交易 Agent 架构设计

> 从旧 Claude 账号的文档导出（2026-11-19）。这是 2026-10-29 的最初设计，后来按小资金改过，以“更新”一节和 CLAUDE.md 为准。

Oct 29, 2026 · @Minglu

## 结论摘要

推荐用 **NautilusTrader**（回测与实盘同一套代码，原生支持 IBKR）作为交易内核，Claude 只做“研究员 + 提案人”，最终是否下单由确定性的期望值计算和风控代码决定。这样“无情绪、最理性”是靠规则和数学保证的，而不是靠大模型的判断。

**推荐技术栈**

- 交易内核：NautilusTrader（备选：ib\_async + 自研轻量引擎）
- IBKR 连接：IB Gateway（无界面，docker 化）+ TWS API，经 NautilusTrader 的 IB 适配器或 ib\_async
- 研究与快速回测：vectorbt / pandas，做参数和因子筛选
- 基本面数据：SEC EDGAR（XBRL 报表，免费）+ 一个付费数据源（如 FMP、Polygon），IBKR 自身的基本面接口不稳定，不宜作唯一来源
- AI 层：Anthropic API（Claude），结构化输出 + 工具调用，只产出 JSON 提案
- 存储与监控：PostgreSQL/TimescaleDB 存行情、决策日志；Grafana 看板；Telegram/邮件告警

**五条核心原则**

1. LLM 不直接下单：Claude 的输出永远要经过确定性风控层才可能变成订单。
2. 每笔交易必须有正的净期望值：扣除手续费、点差、滑点后 E\[收益\] > 门槛，否则不交易。“不交易”是默认动作。
3. 规则写死在代码里，运行时不可被模型或人临时修改（改规则要走代码评审 + 重新回测）。
4. 回测、纸面、实盘同一套代码，只换数据源和账户。
5. 所有决策可复盘：每一次提案、打分、风控结果、成交都落库。

## 更新：按长线、小资金调整后的方案

10 月 29 日确认了约束条件：只做美股，持有一年以上，投入约 2000 欧。在这个规模下，高频交易和重型引擎都不划算，所以第一版做了下面这些调整，代码见 [ibkr-agent PR #1](https://github.com/minglu-prime/ibkr-agent/pull/1)。

| 方面 | 原方案 | 第一版实现 |
| --- | --- | --- |
| 交易内核 | NautilusTrader | ib\_async + 自研的纯函数决策和风控（每周或每月运行一次） |
| 期望收益 | 信号历史胜率 × 盈亏 | 报表基线（自由现金流收益率 + 增长 − 杠杆惩罚）+ Claude 有上限的调整 |
| 仓位 | 分数 Kelly | 等权，最多 6 只，单笔不低于 $200 |
| 换仓 | 净期望值更优才换 | 买入线：超额 ≥ 2% + 摊薄成本；卖出线：超额 < 1% |
| 杠杆 | 1.0× | 不用融资，欧元需先换成美元 |

小资金另外要注意几点：每单最低约 $1 的佣金，会让小仓位来回一次的成本接近 1%；股价超过约 $350 的股票买不了整股；欧盟散户通常买不了美国 ETF，所以大盘基线只用来做比较。

## 开源项目对比

真正能拿来跑 IBKR 实盘的只有前三个；其余的适合拿来做研究或借鉴思路。下表是我基于已有知识的判断，本次没有逐个核对最新版本，建议动手前再看一眼各仓库的活跃度。

| 项目 | 定位 | IBKR 实盘 | 优点 | 缺点 | 在本系统中的用法 |
| --- | --- | --- | --- | --- | --- |
| [NautilusTrader](https://github.com/nautechsystems/nautilus_trader) | 事件驱动交易引擎（Rust 内核 + Python） | 原生适配器 | 回测/实盘同代码；内置订单状态机、风控引擎、手续费模型；活跃维护 | 学习曲线陡，API 仍在演进 | **首选内核** |
| [ib\_async](https://github.com/ib-api-reloaded/ib_async) | IBKR TWS API 的 asyncio 封装 | 是 | 轻量、直观，ib\_insync 的社区继承者 | 只管连接，回测/风控/订单管理全要自己写 | 备选方案；也适合写账户对账、数据抓取脚本 |
| [LEAN](https://github.com/QuantConnect/Lean) | QuantConnect 的全功能引擎（C#，支持 Python） | 支持（本地实盘通常需 QC 付费账号） | 最成熟，数据、手续费、滑点模型齐全 | 重，偏向其云生态，接入 Claude 不如 Python 自然 | 如果愿意用 QC 云，可替代 Nautilus |
| [backtrader](https://github.com/mementum/backtrader) | 经典 Python 回测框架 | 有旧 IB 接口 | 文档和示例多 | 基本停更，实盘不可靠 | 不推荐用于实盘 |
| [vectorbt](https://github.com/polakowo/vectorbt) | 向量化回测 | 否 | 极快，适合大规模参数扫描 | 不模拟订单细节 | 研究阶段筛策略、做稳健性检验 |
| [Qlib](https://github.com/microsoft/qlib) | 微软的因子/ML 研究平台 | 否 | 因子库、模型训练流水线完整 | 偏 A 股数据，实盘需自己对接 | 可选：产出量化信号作为输入 |
| [TradingAgents](https://github.com/TauricResearch/TradingAgents) | 多 LLM Agent 投研框架 | 否 | 分析师/多空辩论/风控角色分工的思路可借鉴 | 研究原型，不是生产系统 | 借鉴其 Claude 提示词和角色设计 |
| [IBC](https://github.com/IbcAlpha/IBC) + [ib-gateway-docker](https://github.com/gnzsnz/ib-gateway-docker) | IB Gateway 自动登录与容器化 | 运维组件 | 解决每日重启、自动登录 | 2FA 仍需处理 | **必用**，让 Gateway 7×24 在线 |

## 整体分层架构

系统分六层，数据自上而下流动；Claude 和量化信号并列作为输入，决策引擎和风控层都是纯代码，任何订单都必须依次通过这两层。

&#91;embedded content: 系统分层架构 · 6 层，从数据到复盘\]

监控层记录的实测手续费和滑点会回填决策引擎，让成本估计随实盘数据越来越准。研究类任务按日或按财报事件触发，执行层按行情事件运行，两者异步解耦，Claude 的延迟和故障不会卡住下单与撤单。

## Claude 在系统中的位置

Claude 擅长读懂非结构化信息，不擅长稳定地做算术和概率校准。所以让它把报表、电话会、新闻变成结构化的、可验证的判断，数字计算和最终决定交给代码。

|  | Claude 做 | Claude 不做 |
| --- | --- | --- |
| 研究 | 读 10-K/10-Q、财报电话会纪要、新闻，提取关键变化、风险点和论点 | 自己编数字；财务指标一律从 XBRL/数据源取，由代码计算 |
| 提案 | 输出 JSON：标的、方向、论点、反方论点、信心等级、失效条件、引用原文 | 决定仓位大小、价格、是否下单 |
| 复盘 | 每日/每周生成复盘报告，指出偏离预期的交易 | 在运行时修改风控参数或策略代码 |
| 异常 | 解释异动（停牌、并购公告）并建议暂停 | 绕过熔断 |

**如何让 Claude 的输出也“无情绪”**

- 结构化输出：用工具调用/JSON Schema 强制格式，不合格式即丢弃，默认不交易。
- 强制反方：同一标的跑“多方分析师”和“空方分析师”两次，再让一个“裁判”调用给出最终信心，减少单一叙事偏差。
- 校准：把 Claude 的信心等级当作一个特征，用历史纸面交易结果拟合它和实际胜率的关系；未校准前只给很小权重。
- 防未来函数：回测时只给 Claude 当时可见的文档。注意模型本身有训练截止日前的“未来记忆”，所以 LLM 信号的可信评估只能靠截止日之后的纸面交易。
- 成本控制：研究类任务按日或按财报事件触发，不在每个 tick 调用；用 prompt caching 缓存长文档和系统提示。

## 理性决策框架

每个候选交易用同一个公式打分：只有扣除全部成本后的净期望值为正且超过门槛，才进入风控审查。四个输入对应你说的报表、基线、位置、手续费。

```latex
\text{NetEV} = p_{win} \cdot \bar{G} - (1 - p_{win}) \cdot \bar{L} - C_{commission} - C_{spread} - C_{slippage} - C_{borrow}
```

| 输入 | 含义 | 来源 | 由谁计算 |
| --- | --- | --- | --- |
| 报表（基本面） | 估值分位、盈利质量、财报超预期程度、Claude 提取的定性变化 | EDGAR XBRL + 数据源 + Claude | 代码算指标，Claude 给定性评分 |
| 基线 | 信号必须跑赢的对照：买入持有 SPY、同行业 ETF、随机入场 | 回测与纸面历史 | 代码 |
| 位置（仓位） | 当前持仓、相关性、行业暴露、可用保证金 | IBKR 账户实时数据 | 代码 |
| 手续费 | 佣金 + 交易所/清算费 + 点差 + 滑点 + 融券费 | IBKR 费率表 + 实测成交 | 代码 |

**关键细节**

- p\_win、平均盈亏来自该类信号的历史统计（回测 + 纸面），不来自 Claude 的话。Claude 的信心只通过校准后的调整系数影响 p\_win。
- 手续费估计：IBKR Pro 美股固定费率大约是每股 $0.005、每单最低 $1（记忆数字，接入前请对照官网费率表）。小额交易时最低收费会吃掉大部分优势，所以要设最小下单金额。
- 滑点模型：先用保守假设（如半个点差 + 按成交量占比的冲击成本），纸面和实盘后用真实成交与下单时中间价的差值重新拟合。
- 仓位：用分数 Kelly（建议 1/4 Kelly 或更低）和波动率目标取小者，再被风控上限截断。
- 换仓也要算成本：只有新机会的 NetEV 减去卖出旧仓位的成本后仍更优，才换。这样可以自然抑制过度交易。

## 风控硬约束与熔断

风控层是纯代码、无模型参与，任何一条不过就拒单。下面的数值是起步建议，需要按你的资金规模和风险偏好定。

| 类别 | 规则 | 建议起步值 |
| --- | --- | --- |
| 单笔 | 单笔最大亏损（按止损距离计） | 账户净值 0.5% |
| 单标的 | 单标的最大仓位 | 净值 5–10% |
| 组合 | 单行业暴露、总杠杆 | 行业 25%，总杠杆 1.0×（即不加杠杆） |
| 日内熔断 | 当日亏损达到阈值即停止开新仓 | 净值 2% |
| 回撤熔断 | 从高点回撤达到阈值即减半仓位并人工审查 | 10% |
| 订单 | 只用限价单；限价偏离中间价不超过阈值；单日下单次数上限 | 0.5%；20 单/日 |
| 数据 | 行情过旧、报价异常、账户与本地持仓不一致 → 暂停 | 行情超 5 秒未更新 |
| 时间 | 开盘后、收盘前、财报发布前后的黑名单窗口 | 开/收盘各 15 分钟 |
| 系统 | Claude API 超时/报错 → 视为“无提案”；Gateway 断连 → 撤销未成交单 | 始终生效 |

另外保留一个人工总开关（kill switch）：一条命令即可撤销全部挂单并禁止新开仓。在 IBKR 账户端也设置订单金额上限等预设作为最后一道防线。

## 上线路径

从零到正式资金实盘建议至少 4–6 个月，每一阶段只有过了关卡才进入下一阶段。步骤按顺序执行：

1. **研究与回测（约 4–6 周）**：用 vectorbt 筛信号，再在 NautilusTrader 中用真实费率和滑点做事件级回测。
   - 关卡：样本外扣费后跑赢基线；参数小幅扰动后仍稳定；walk-forward 验证通过。
2. **纸面交易（至少 2–3 个月）**：同一代码连 IBKR Paper 账户，Claude 全流程在线。
   - 关卡：纸面结果与回测预期偏差在可解释范围内；没有未处理的系统故障；风控拦截日志全部复盘过。注意 Paper 账户的成交比实盘乐观。
3. **小资金实盘（至少 1–2 个月）**：用计划资金的 5–10% 跑，重点量真实滑点和手续费。
   - 关卡：实测成本不高于模型假设；未触发非预期熔断。
4. **逐步放大**：每次加仓不超过上一档的 2 倍，回撤熔断触发即退回上一档。

每个阶段都用同一个配置文件切换环境（backtest / paper / live），不允许实盘代码有独立分支。

## 代码结构与下一步

建议一个 Python monorepo，每一层一个包，风控和执行不依赖 AI 层，可以单独测试。

```
ibkr-agent/
  config/            # backtest.yaml / paper.yaml / live.yaml，风控参数也在这里
  data/              # 行情、EDGAR 报表、新闻采集与入库
  research/          # Claude 调用：提示词、JSON Schema、多空辩论与裁判
  signals/           # 量化因子与信号统计
  decision/          # NetEV 计算、手续费/滑点模型、仓位计算
  risk/              # 硬约束与熔断（纯函数 + 单元测试覆盖）
  execution/         # NautilusTrader 策略与 IB 适配器配置
  monitor/           # 日志、告警、每日复盘
  tests/
  docker-compose.yml # ib-gateway + postgres + agent + grafana
```

**建议的第一个里程碑**：跑通 IB Gateway（Paper）→ NautilusTrader 连接 → 一个简单的按日再平衡策略 → Claude 读一份 10-Q 并输出 JSON 提案 → NetEV + 风控审查 → Paper 下单并落库。先打通这条链路，再迭代策略本身。
